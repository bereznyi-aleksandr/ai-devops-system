# Установка сервера Завода

## 1. Сборка пакета (на машине разработки или в CI)

    python3 -I zavod/ops/server/build_server_package.py OUT_DIR

Результат — один архив `zavod-server-<коммит>.tar` и рядом `MANIFEST.sha256`
(опись: сумма SHA-256 — контрольная сумма — каждого файла). Строка итога:
`ZAVOD_SERVER_PACKAGE=OK file=… files=… sha256=… manifest_sha256=…`.
Тот же коммит даёт тот же архив с той же суммой (проверяет CI, задание `server_package`).
CI хранит собранный архив и опись как приложение к прогону (artifact — файл, который GitHub хранит
при прогоне 30 дней) `zavod-server-package`; строка итога сборки в журнале прогона — квитанция суммы.

В архив входят: пакет базы H1.31, ядро с модулями по `package-lock.json`, файлы движка,
файлы сервера и ячейки, Node.js 22, Flowable REST и драйвер базы — внешние части по
закреплённым суммам. Тесты, проверки CI, файлы Windows и файлы с секретами в пакет не входят.

## 2. Доставка пакета на сервер по SSH (защищённый вход администратора)

Администратор копирует архив и опись на сервер и сверяет сумму архива там же
(строка `sha256=…` из итога сборки):

    scp zavod-server-<коммит>.tar MANIFEST.sha256 admin@<сервер>:/root/
    ssh admin@<сервер> sha256sum /root/zavod-server-<коммит>.tar

Сумма не совпала — архив не распаковывать, скопировать заново.

Перед распаковкой администратор сверяет SHA-256 архива с неизменяемой квитанцией доверенного CI,
полученной независимо от переданного файла, а также проверяет подлинность SSH-сервера. Если доверенного
источника суммы нет — установка запрещена. Криптографическая подпись необязательна лишь при действии
этой цепочки доверия.

## 3. Установка (на чистой Ubuntu 24.04, от root)

    tar -C /root/zavod-pkg -xf zavod-server-<коммит>.tar
    bash /root/zavod-pkg/zavod/ops/server/install_server.sh /root/zavod-pkg \
      --session-fs-size 64M --intake-fs-size 192M --intake-fs-inodes 2048 \
      --intake-journal-size 16M --min-free 1G

Размеры разделов в примере — как в CI; на настоящем сервере их задаёт оператор.

Порядок внутри установщика:

1. Сверка каждого файла пакета с описью. Файл изменён или лишний — отказ, ничего не ставится.
   До сверки сумм: в пакете только обычные файлы и папки (символическая ссылка — ярлык на другой
   файл — или жёсткая ссылка — второе имя того же файла — отказ); права каждого файла — как в описи.
2. Пакеты системы из закрытого списка: PostgreSQL 16, nftables, python3, unzip, zip, Java 21.
3. Node.js 22 из пакета в `/opt/zavod/node-<версия>`, ссылка `/usr/bin/node`.
   Другой Node.js на этом пути — отказ. Архив распаковывается во временную папку и переносится
   целиком. Уже существующая папка Node.js сверяется с архивом пакета: тот же список файлов, те же
   байты, ссылки и права, владелец root; номер версии сверяется полностью (22.23.3).
4. Файлы выпуска в `/opt/zavod/releases/<коммит>`, ссылка `/opt/zavod/current`.
   Прежние выпуски остаются. Копия выпуска проверяется заново (суммы, типы файлов, права), и
   установщик перезапускает себя из неё: дальше всё ставится только из закрытой копии root.
   Уже существующие каталоги /opt/zavod/node-<версия> и /opt/zavod/releases/<коммит> перед
   использованием проверяются по байтам, владельцам, режимам файлов и правам всех каталогов.
   Совпадение имени каталога или номера версии не является доказательством неизменности.
   Несоответствие — отказ до запуска. (Проверку делает `verify_tree.py` из пакета: каждый файл и
   папка — владелец root, без записи для группы и других, без жёстких ссылок — второго имени того
   же файла; папки выше тоже принадлежат root и закрыты на запись.)
5. PostgreSQL 16 только на сокете (вход из сети закрыт). Цепочка базы ставится один раз;
   на время цепочки — временный вход владельца кластера под ролями цепочки, сразу после неё
   он убирается. Итоговая проверка базы — при каждом запуске (`DB_CHAIN=OK`).
6. Ячейка: учётные записи (и `zflowable` движка), клетка, привратник, посредник, фильтр, приём
   архивов (`install_cell.sh`, строка `ZAVOD_CELL_INSTALL=OK`). Фильтр сети (nftables) пускает:
   сеансы агента — только к посреднику; движок `zflowable` — никуда; ядро `zkernel` — только к движку
   `127.0.0.1:8091`; службы GitHub, Telegram и копии (`zgithub`, `ztelegram`, `zbackup`) — только
   порт 443 и местный перевод имён сайтов в адреса.
7. Служба ядра `zavod-kernel` включается (запуск — после заполнения файла настроек).
   Файл настроек `/etc/zavod/` создаётся из примера, только если его ещё нет.
8. Служба движка процессов `zavod-engine`: учётная запись `zflowable`, своя база и схема
   `bem_engine`, вход в базу через сокет без пароля (драйвер junixsocket), приём запросов только
   на `127.0.0.1:8091`. Пароль администратора движка установщик создаёт сам, один раз, в файл
   `/etc/zavod/engine_admin.conf` (только root); он не выводится (решение оператора 2026-11-02).
   Строка `ENGINE=OK`.
9. Отчёт: `ZAVOD_SERVER_RELEASE=<коммит> inventory_sha256=… node=…`, опись ОС — строки
   `ZAVOD_SERVER_OS_PACKAGE=<пакет>=<версия>` для пакетов шага 2 и
   `ZAVOD_SERVER_OS=ubuntu-24.04 kernel=… packages=… bom_sha256=…` (сумма списка всех пакетов ОС), и
   `ZAVOD_SERVER_INSTALL=OK`.

Повторный запуск даёт тот же результат (проверяет CI); пароль движка при повторе не меняется.

## 4. Чего ещё нет

- Подключение ядра к движку (ядру нужен доступ к учётной записи администратора движка).
- Прогона пилота P1 на сервере: файл настроек `/etc/zavod/zavod.env` не содержит настроек `P1_*`, а пакет
  не кладёт архив `flowable-rest.war`, который пилот (`zavod/engine/ci/e5_pilot_run.mjs`) сверяет по сумме и
  запускает на своём порту. Пилот на сервере — отдельный шаг со своим файлом настроек.
- Служб `zgithub`, `ztelegram`, `zbackup` ещё нет: фильтр готовит для них только сеть. Граница:
  nft ограничивает эти три сервисные учётные записи только портом 443 и локальным DNS, но не адресом
  получателя; адреса и имена проверяют соответствующие службы по закрытым спискам. Root и администратор
  под этот фильтр не подпадают. Контроль этих списков и отказов — обязательная отдельная проверка до
  эксплуатации.
- Версии программ ОС не закреплены пакетом; барьер И.7а доверяет конкретной, отдельно учтённой и
  проверенной версии образа Ubuntu/apt на сервере; изменение этой версии требует независимой
  совместимости и повторных проб И.13. Фактические версии называет отчёт установщика (шаг 9).
